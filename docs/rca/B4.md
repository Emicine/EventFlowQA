# RCA B4 : Le code promo expiré reste accepté

## Symptôme observé

Avec `SEED_BUGS=true`, saisir le code `EXPIRED` sur la page d’un événement n’affiche pas le message « Promo code expired ». L’utilisateur est envoyé vers la page de paiement et la commande bénéficie de la remise.

## Impact (pour l'utilisateur, pour l'entreprise)

- Pour l’utilisateur : un code expiré est accepté et le prix affiché est réduit.
- Pour l’entreprise : une remise non valide est accordée, ce qui réduit le montant de la commande.

## Preuves (commandes, résultats, capture de la trace, ligne de code)

- Test UI : `pytest tests/ui/playwright/test_booking_ui.py::test_expired_promo_code_shows_error -p no:rerunfailures` — échec **3 fois sur 3**. L’assertion attend « Promo code expired », mais aucun élément `.notice-err` n’est trouvé ; la page est `/checkout/...`.
- Test API : `pytest "tests/api/test_booking_rules.py::test_rm4_promo_codes[EXPIRED]"` — l’API renvoie **201**, alors que le test attend **400**.
- Trace Playwright : `POST /api/orders`, payload avec `promo_code: "EXPIRED"`, réponse **201 Created** et `total_cents: 2975` (**29,75 €**). Le prix initial était **35,00 €** ; la remise de 15 % a été appliquée.
- Code : `backend/app/routers/orders.py`, ligne 34 : la condition de vérification de l’expiration inclut `and not settings.seed_bugs`. La ligne 36 lève l’erreur 400 attendue.
- Pipeline : `.github/workflows/ci.yml`, ligne 51 : l’étape UI contient `continue-on-error: true`, donc son échec n’échoue pas le job.
- Capture de trace : à joindre au rapport d’anomalie. Ne pas inclure l’en-tête `Authorization`.
- Sortie SQL de vérification de la date `EXPIRED` : à ajouter après exécution de la requête de l’étape 6. Elle n’a pas encore été relevée dans les éléments disponibles.

## 5 Pourquoi

| Pourquoi | Réponse | Preuve |
|---|---|---|
| 1. Pourquoi le test UI échoue-t-il ? | Le message « Promo code expired » n’apparaît pas ; la page arrive au paiement. | Échec de l’assertion ligne 52 de `qa/tests/ui/playwright/test_booking_ui.py` et URL `/checkout/...` dans le résultat du test. |
| 2. Pourquoi l’utilisateur arrive-t-il au paiement ? | L’API accepte la commande contenant le code expiré. | Trace : `POST /api/orders`, payload `promo_code: "EXPIRED"`, réponse 201. |
| 3. Pourquoi l’API accepte-t-elle le code ? | La vérification d’expiration ne lève l’erreur que lorsque `settings.seed_bugs` est faux. Avec le mode bug activé, `not settings.seed_bugs` vaut faux. | `backend/app/routers/orders.py`, lignes 34–36 ; test API : 201 reçu au lieu de 400. |
| 4. Pourquoi une remise est-elle appliquée ? | Après la validation, le total est calculé en appliquant le pourcentage du code promo. | Trace : `total_cents: 2975`, soit 15 % de moins que 3500 centimes. |
| 5. Pourquoi un échec UI peut-il ne pas bloquer le pipeline ? | L’étape des tests UI est marquée pour continuer en cas d’erreur. | `.github/workflows/ci.yml`, ligne 51 : `continue-on-error: true`. |

## Cause racine

La condition de validation de l’expiration dans `_validate_promo` désactive volontairement le rejet quand `SEED_BUGS=true` (ligne 34). L’erreur 400 à la ligne 36 n’est alors jamais levée. Le pipeline a aussi une faiblesse de détection : l’échec de l’étape UI est toléré par `continue-on-error: true`.

## Actions correctives

- Produit : faire rejeter par l’API tout code promo expiré, indépendamment de la configuration utilisée pour les tests.
- Processus de test : rendre les échecs UI bloquants dans le pipeline et conserver un test de non-régression couvrant un code expiré.

## Comment vérifier que c'est corrigé

Avec `SEED_BUGS=false`, vérifier que le test API reçoit le statut 400, que le test UI affiche « Promo code expired » et que la commande n’est pas créée avec une remise. Vérifier également qu’un échec UI fait échouer le job CI.
